### fix(tokensaver): RTK no longer rewrites ordinary text as the output of a CLI

- When RTK could not resolve a tool's command (an MCP result, a fetched page, a file read through a wrapper) it chose a CLI filter from the text alone on a single matching pattern, and the filter kept only the lines it recognises. Measured on 463 ordinary repository files, 445 were claimed by a filter and the full pipeline kept about 17% of the text. Content selection now needs two distinct patterns of a filter, or one entry from its new `match.strongPatterns` (multi-word lines a command prints and prose does not, such as `^diff --git <a> <b>`). Selection patterns are matched case-sensitively; the include and drop lists are unchanged. On 917 files one is still claimed.
- Loose patterns fixed: `gh` (a word ending in x), `git-branch` (a markdown bullet) and `test-go` (prose starting with "fail"). Selection by command is unchanged.
- RTK results for texts of 4 KB or more are memoized (at most 1024 entries and 64 MB): a tool result that comes back on every turn costs about 0.4 ms instead of about 114 ms for a 73 KB result.
- Accessibility-tree snapshots from browser tools are compacted before truncation: leaf nodes with no name, text or state (`img`, `generic`, `presentation`, `none`) are dropped, and a two-space indentation is halved. Nothing an agent can act on or read is removed, and element refs are kept.
